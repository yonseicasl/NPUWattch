8 declared exclusions (INFO — deliberate, not modeling gaps)
  • scalar core (with its L1 I-cache / D-cache, branch predictor and TLBs) is excluded from the energy model per PyTorchSim author guidance (2026-07-25, negligible area/power vs the systolic/vector datapath); gem5 stats are read only for numCycles and the instruction counts matching CustomMatMul(wVpush|iVpush|vpop)? and CustomV(exp|exp2|erf|tanh|sin|cos)
  • CustomVlaneIdx instruction counts are deliberately not collected: it is lane-index generation, not an SFU op, and its energy is negligible
  • BAR / MEMORY_BAR (barrier) instruction counters are not collected: synchronization is control-side work (scalar-core scope) and the stall time it causes is already inside total_exec_cycles, so it is charged as leakage over the window
  • VCIX serializer/deserializer (the vector <-> systolic-array interface) is not modeled as a separate component: its push/pop events are already charged at both endpoints (w_reg writes, vpu_spad reads/writes), and PyTorchSim exposes no serdes size parameters — the remaining mux/wire datapath is second-order
  • DRAM background/standby power and the NPU-side memory controller / HBM PHY are not charged: vendor IDD/standby currents for HBM are not public (no open HBM power tool exists), so the dram compound charges command energies only (activate / read / write / refresh, constants cited from O'Connor & Chatterjee et al., MICRO 2017); the on-chip consequences of DRAM traffic (VMEM fills/drains, DMA engine, NoC flits) are charged by their own compounds
  • activity stat 'CustomMatMul' (total 2 across 1 window(s)) is not charged — waived in projection 'pytorchsim': compute is charged per systolic active cycle (Option A: systolic_active_cycles x lanes^2 = MACs); this instruction count is a redundant counter of the same work
  • activity stat 'comp_gemm_ops' (total 576 across 1 window(s)) is not charged — waived in projection 'pytorchsim': COMP GEMM op counter: the same GEMM work is charged per systolic active cycle (CustomMatMul action); charging both would double-count
  • activity stat 'comp_vector_ops' (total 1 across 1 window(s)) is not charged — waived in projection 'pytorchsim': COMP vector op counter: the same vector work is charged per vector-unit active cycle (vpu compound actions); charging both would double-count
